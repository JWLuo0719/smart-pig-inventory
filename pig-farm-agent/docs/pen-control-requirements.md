# 以猪圈为单位的独立控制：需求、前提与安全边界

> **状态：范围变更提案。** 现有 V1 明确写的是"第一阶段只做只读分析和建议，**不直接控制风机、喂料器等设备**"
> （`docs/product-brief.md` 第 5 行、`docs/product-development-plan.md` §第一阶段与 §V1 排除项）。
> 客户现在要求"每圈独立控制"，这是对产品边界的显式变更，需客户确认并重排优先级。

---

## 0. 一句话结论

**每圈独立控制 = 计量层 × 执行层 × 安全层，三层叠加。**

三句话记住边界：

1. **执行器粒度决定控制粒度**——现场若是"一栋一风机、一条料线管整栋"，软件再强也控不到圈，必须先改硬件；
2. **视觉计数是慢变量，只能当优化输入，不能当安全输入**——安全和环控必须由环境传感器 + 硬联锁驱动；
3. **控制追求"稳、可用、安全"，不是"准"**——照片没传上来不能变成不喂料、不通风。

---

## 1. 控制对象清单（按圈粒度）

| 控制对象 | 典型执行器 | 每圈独立的物理前提 | 控制目标 | 风险等级 |
|---|---|---|---|---|
| 饲喂/下料 | 料线绞龙、定量杯、智能料槽/饲喂站 | 每圈独立料线，或每圈独立落料阀 | 按圈定量、按体重曲线给料 | 中（多喂浪费、少喂掉膘） |
| 饮水/加药 | 水阀、水表、加药泵 | 每圈独立水阀与水表 | 按圈供水、饮水量异常告警 | **中高**（断水数小时即伤亡） |
| 通风 | 风机（定频/变频）、小窗、导流板 | 每圈独立风机或分区风阀 | 按"头数 × 体重"算最小通风量 | **高**（停风 = 闷死） |
| 降温 | 湿帘水泵、喷淋、滴水 | 分区控制 | 按圈温度 | **高**（高温高湿致死） |
| 加热/保温 | 加热灯、地暖、热风炉 | 每圈 | 仔猪保温区温度 | **高**（仔猪冷应激） |
| 照明 | 灯具 | 每圈或每栋 | 光照时长 | 低 |
| 清粪 | 刮粪板、冲水 | 栋级/单元级 | 定时运行 | 低 |
| 报警 | 声光、短信/企业微信/钉钉 | 每圈 | 越限告警 | **高（兜底手段，必须独立可用）** |

**先划出第一批可自动化的动作**：照明、报警、清粪定时（低风险）。
通风最小量、下料量属于高风险动作，建议长期保留"人工确认"或只做建议——这是控制系统的常见落地方式，不是能力不足。

## 2. 现场核查清单（能不能做，先勾这个）

这一页决定项目可行性，**在写任何代码之前必须拿到答案**：

| # | 核查项 | 为什么必须问 | 不合格的后果 |
|---|---|---|---|
| 1 | 每圈是否有独立风机/风阀？ | 决定通风能否按圈 | 只能做栋级通风，需求不成立 |
| 2 | 每圈是否有独立下料执行器？ | 决定能否按圈定量饲喂 | 只能整栋投料，精准饲喂无从谈起 |
| 3 | 是否有本地控制柜/PLC？通讯协议（Modbus/485/IO/网关）？ | 决定集成方式与工作量 | 需整体更换控制柜，成本剧增 |
| 4 | 舍内网络覆盖与断网概率？ | 决定架构是"云控"还是"边缘闭环" | 云控在弱网舍内必然出事故 |
| 5 | 断电处理：UPS/发电/应急开窗？ | 停风是致死级风险 | 一次停电可能整栋损失 |
| 6 | 每圈是否有温湿度/氨气/CO₂ 传感器？ | 安全回路必须有独立输入 | 只能靠视觉兜底 = 不可接受 |
| 7 | 夜班与响应时间？多久能到现场？ | 决定自动化的兜底方式 | 报警无人处置 = 报警无效 |
| 8 | 过去一年死淘主因？ | 决定控制优先级与 ROI | 投入方向可能完全错 |
| 9 | 客户是否接受"影子期"与责任条款？ | 决定商务可行性 | 出事后责任无法界定 |

## 3. 三层架构与三条铁律

```
感知层（视觉计数 + 环境传感器 + 采食/饮水）
        ↓
决策层（策略引擎 + 安全联锁 + 白名单）
        ↓
执行层（PLC / 网关 / 本地控制器 → 执行器）
        ↑
安全兜底（独立于 AI 的硬联锁：超温开窗、断电开窗、断网保通风）
```

1. **AI 不直连执行器。** 模型输出只能变成"设定值建议"，经规则层与安全联锁后才下发。
2. **安全动作不依赖视觉。** 通风/降温/断水报警由环境传感器 + 硬联锁驱动；**摄像头故障不得导致环控失效**。
3. **fail-safe 默认。** 断网、断服务、模型异常、数据缺失 → 回到安全默认（通风不停、开窗、报警），
   **而不是"保持最后一条指令"**。

## 4. 计量误差怎么传到控制（最容易被忽略的坑）

- 计数 ±5%，200 头的圈就是 ±10 头。按头数直接下料 → 系统性多喂或少喂；多喂的钱每天累积，少喂直接掉膘。
- 所以控制回路必须**闭环**：按圈下料 → 采食量/料槽余料/体重抽样 → 修正，而不是"数出多少就喂多少"。
- **计量数只调"设定值"，不调"安全阈值"。** 安全阈值按体重/日龄/头数的保守上限设定，且允许人工覆盖。
- **数据缺失要有降级路径**：照片没传上来、模型不可用 → 退到按日龄标准曲线，绝不能停止饲喂或通风。

### 关键设计：把"头数"当慢变量用

这是让项目变简单的核心判断：

> **头数是慢变量。** 一个批次内，栏舍头数只在转群、出栏、并栏、死亡时变化。
> 控制系统需要的是"**最近一次已复核的存栏快照**"，不是每分钟实时计数。

推论：
- 盘点需求（尤其"多日多次盘点取综合值"）的定位从"独立产品"变成**控制系统的参数标定环节**——
  一次可信盘点管一个批次，用不着实时精确；
- 视觉计数不参与安全回路，精度压力大幅下降；
- 控制回路日常靠**连续量**运转：采食量、饮水量、体重、温湿度；
- 视觉的真正价值在**异常检测**：某圈采食/饮水掉了、猪只堆叠不动、栏舍空了或密度异常。

**已复核的盘点数才允许作为控制输入**（沿用"未批准模型不得自动写入业务值"的既有原则）。

## 5. 权限、责任与合规

- **三档运行模式**：`建议（人工执行）` → `半自动（人工确认后下发）` → `自动（仅白名单动作）`；
- **留痕**：谁改了设定值、谁切到自动、每次指令与执行回执（含超时/失败/被本地控制器拒绝）；
- **责任条款必须写进合同**：系统建议/执行与现场处置的责任边界、异常工况的赔偿划分；
- **影子期**：系统只算不下发，跑满一个完整批次，对比"系统建议 vs 人工实际"，
  证明建议优于现状再进入半自动——这既是技术验证，也是取得客户信任的唯一办法；
- **保险**：涉及生命安全的自动动作，建议明确保险与免责范围后再上线。

## 6. 与现有系统 / 金蝶的关系

| 事项 | 做法 |
|---|---|
| 主数据 | 复用同一套 `猪场 / 栋 / 栏舍` 三级树与 `penId`，**不新建第二套编码**；控制寻址与计量归因用同一主键 |
| 记录 | 控制动作 = 生产事件（饲喂/环控），与盘点报告同源，可对账 |
| 金蝶 | 饲料、药品、水电等投入品消耗建议由本系统出"**按圈消耗清单**"，由 ERP 记账，避免两套账 |
| 本仓库现状 | 只有 `suggested_actions` **文本**，**没有任何执行器接口**。接入需新增：执行器适配层 + 指令审计表 + 安全联锁配置 + 回执状态机 |
| 质量属性变化 | 盘点追求"**准**"（MAE、复核），控制追求"**稳**"（可用性、连续性、失效安全）——验收指标要分开写 |

## 7. 分阶段路线（每阶段有交付与止损点）

| 阶段 | 内容 | 止损点 |
|---|---|---|
| **P0 影子模式** | 只算不下发，输出建议设定值，人工执行；记录对比数据 | 建议准确率不达标 → 不进 P1 |
| **P1 半自动** | 低风险动作自动（照明/报警/清粪定时）；高风险动作人工确认 | 误动作率/回执失败率超标 → 回退 |
| **P2 闭环** | 通风/下料自动执行；需独立安全联锁 + 硬件改造验收 + 合同与保险到位 | 任一安全联锁不通过 → 不上线 |

**交付节奏的现实预期**：硬件改造 + 现场调试 + 影子期，至少跨一个生产批次，不是软件迭代能压缩的。

## 8. 需要客户回答的决策问题

1. **控什么**？从 §1 的执行器清单里勾选范围（先小后大）。
2. **现场执行器粒度是否支持每圈独立**？（拿 §2 核查表去现场逐项填）
3. **断网/断电时期望的行为**是什么？（这直接决定架构与硬件清单）
4. **误控的责任怎么划**？是否接受影子期与免责条款？
5. **计量不准或照片缺失时**，系统该降级到什么行为？
6. **控制数据是否回写金蝶**？还是本系统出清单、ERP 记账？
7. **预算口径**：硬件改造 + 软件 + 运维分别谁出？

## 9. 商务影响（报价与风险）

- **报价口径变化**：从"栏舍数 × 分析频次"变成"**控制点数 × 硬件改造 + 软件订阅 + 运维**"，
  并计入安全责任溢价；
- **验收指标要重写**：盘点侧看 MAE 与复核率；控制侧看可用率、指令回执成功率、失效切换时间、零安全事故；
- **风险敞口**：误控死猪的损失远大于精准饲喂省下的料钱——**这是决策的核心权衡**，
  建议在 P0 阶段就用客户自己的数据把"省多少 vs 赔多少"算清楚，再决定 P2 是否推进。
