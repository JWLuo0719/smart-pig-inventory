# 栏舍级拍照盘点：需求解读与问题归因

本文把你口述的 8 条需求 + 4 个"存在问题"翻译成系统语言，并指出这 4 个问题其实是同一件事的四个侧面。
末尾列出必须由业务方确认的口径（**这些不确认，系统只能猜，猜错就是数不准**）。

> 读法假设（若是别字请纠正）：**"兰舍" = 栏舍**；**"料槽折档" ≈ 料槽遮挡**（料槽挡住猪身）；
> "栋/楼栋" = 一栋猪舍（building）；**栏舍 = 圈栏（pen）**，即"1 栋有 20 个栏舍"里的最小盘点单位。

---

> **范围变更提醒（2026 后续确认）**：客户现已提出"以猪圈为单位的独立控制（每圈独立控制）"。
> 本文 8 条需求全部是**感知与计量**，不含任何执行器需求；控制侧的前提、安全边界与现场核查清单
> 见 `docs/pen-control-requirements.md`。定位上，本文的盘点能力是控制系统的**参数标定环节**
> （头数是慢变量：一次可信盘点管一个批次），不是独立产品。

## 1. 一句话：这 8 条需求到底要什么

要一条能站得住的等式：

> **某一组照片/视频（证据） ⟶ 只属于某一个栏舍（归属） ⟶ 拍全了、没被挡住（覆盖） ⟶ 每头猪只算一次（去重） ⟶ 得到一个可追溯、可复核、可复现的该栏舍猪只数量**

拆开就是 4 件事，8 条需求全是它们的组合：

| # | 要解决的事 | 对应需求 |
|---|---|---|
| A | **归属**：这张照片/视频是哪个栏舍的 | 1、2、4 |
| B | **覆盖**：这个栏舍被拍全了吗、有没有被料槽挡住 | 3、8 + 存在问题 1、2 |
| C | **去重**：同一头猪不能被算两次（同照片重传 / 跨视角 / 跨栏舍） | 4、7、8 |
| D | **可信与留痕**：数字从哪来、谁能改、改了什么 | 4、5、6 + 全程审计 |

另外两条是**产品形态约束**，不是算法问题：
- **弱网优先**（需求 3）：采集与计算必须解耦，"先拍后传、出栏舍再传、结果稍后回填"是一等公民，不是降级方案；
- **主数据外部权威**（需求 1）：猪场/组织来自金蝶 ERP，不是本系统自说自话。

## 2. 逐条翻译

| 编号 | 你的说法 | 真正的业务诉求 | 系统必须提供的机制 |
|---|---|---|---|
| 1 | 猪场组织、栋、栏舍；手工维护编码名称；猪场组织可由金蝶同步 | **三级主数据 + 编码即主键 + 单一真源** | 猪场/栋/栏舍三级树，`farm_code/building_code/pen_code` 全局唯一且稳定；ERP 同步是**主数据下行**（金蝶 → 本系统），本地扩展字段（如栋/栏舍，ERP 里通常没有）**不被同步覆盖**；每条字段标注来源（ERP / 本地），同步要有对账与差异报告，不是覆盖式刷库 |
| 2 | 按栏舍采集照片视频；可先选栏舍再实时拍照，也可拍完再手工选栏舍导入 | **采集物必须携带 penId；两种归因路径都要，但必须留痕** | 采集时强绑定 `penId`（推荐扫码/选栏舍后才允许拍）；事后归位属于"弱绑定"，需记录操作者与时间；**未归属的照片进"待归属"池，不参与任何计数**，否则必然污染数字 |
| 3 | 实时拍照即出盘点数；也可出栏舍后到网络好的地方统一按栏舍上传，再返回结果 | **采集与计算解耦；弱网 outbox；异步出数 + 幂等回填** | 本地暂存原图 → 按栏舍打包 → 断点续传 → 服务端异步推理 → 结果按 `penId + businessDate` 回填到**同一条盘点会话**；重传不能产生第二条盘点（幂等键）；现场要能看到"待上传/计算中/已出数"三态，而不是干等 |
| 4 | 照片去重，同一张只能传一次；每个栏舍有可翻阅的照片/视频库，错的能删 | **证据账本 + 三层去重** | ①**L1 文件级**：`sha256` 唯一约束（同栏舍、跨栏舍都算重复）；②**L2 跨视角**：同一头猪在左/中/右三张里只算一次；③**L3 跨栏舍**：拍到隔壁栏舍的猪不能两边都算。照片库 = 按 `栏舍 × 日期` 的证据账本，可翻阅、可删除（删除受第 5 条约束） |
| 5 | 照片一旦被盘点就锁定，不许删，除非后台改 | **证据不可篡改 + 权限留痕** | 状态机：`已采集(可删) → 已盘点/锁定(不可删) → 已作废(仅后台，留痕)`；删除一律是**逻辑作废 + 审计日志**（谁、何时、为什么），原图与哈希保留，否则"删照片"就等于"抹掉差异" |
| 6 | 月底 25 日盘点，可 23/24 日多次盘点，每天出报告，综合盘点取几天平均 | **盘点会话（session）+ 日报 + 期间聚合** | 每次盘点 = 一个 session（`栏舍 + 业务日期 + 采集集 + 结果 + 复核人`）；日报按天；综合盘点 = 对期间内多个 session 的**可配置聚合**（见 §4 统计前提，平均值不一定是最优口径） |
| 7 | 一栋 20 个栏舍，要给出每个栏舍的数量，隔壁的不能算进来 | **粒度必须到 penId；数量互斥、不重不漏** | 计数的单位是栏舍，不是栋、不是照片；汇总满足 `Σ 栏舍 = 栋 = 场`；越界目标只能归属一个栏舍，判不了的进人工裁决 |
| 8 | 遮挡时可给左/中/右 3 张照片点出数量，同一头猪不能重复计算 | **多视角采集包 + 跨视角去重** | 采集包 `captureKind=left_center_right`，每张带 `viewPosition` 与 `roi`（方向唯一）；跨视角同一头猪去重；并用"分视角合计 vs 全景图"做一致性校验 |

## 3. 那 4 个"存在问题"：其实是三件事

你列的 4 个问题是同一件事的四个侧面，都指向：**照片与栏舍之间缺少可信的绑定关系**。

| 现象 | 根因分类 | 本质 | 系统对策 |
|---|---|---|---|
| 1 张照片照不全栏舍 | **覆盖不足** | 单视角证据不完整，任何计数都是下限值 | 一组照片 = 一个采集包（左/中/右或多张）；ROI 覆盖校验：栏舍区域没被覆盖到就提示重拍；结果是"区间"而非假装精确 |
| 料槽遮挡（猪被挡住） | **覆盖不足（结构性）** | 这是**系统性漏数**，不是随机误差——遮挡位置固定，就会一直少算那几头 | 调整机位/视角、多角度补拍；按栏舍标定遮挡区（同栏舍同机位的固定盲区可用实测头数校准）；质量门不通过时输出 `review_required` 而不是硬报一个数 |
| 照片拍到了旁边栏舍，导致重复点数 | **越界 + 去重** | 一个物理目标被两个栏舍各算一次，两边都虚高 | 栏舍边界 `roi` 裁剪 + 越界判定（目标框落在本栏舍边界内的才算）；拍摄规范（站在本栏舍正前方、避免把邻栏纳入画面）；App 端实时边界提示 |
| 照片不知道是哪个栏舍的 | **归属缺失** | 没有 penId 的证据等于无效证据，一旦混入就污染统计 | 从源头绑定：**每个栏舍贴二维码/NFC 牌，拍照前必须扫码**（比手工下拉选择可靠得多，也免去"事后回忆是哪栏"）；未归属照片进待归属池，不算数 |
| （需求 8）三张照片同一头猪重复计算 | **去重（跨视角）** | 相邻视角有重叠区，重叠区的猪被数两次 | 两条路：① 视觉/几何跨视角实体匹配（难，且要处理卧躺、遮挡）；② **工程解法优先**：把栏舍沿长度切成互不重叠的左/中/右计数区，重叠带只归属一段，用固定机位标定下来——把 AI 难题变成可校验的几何规则 |

**去重的三个层次必须分清**（你的描述里混用了）：

- **L1 文件级**：同一张图（相同 `sha256`）只能存在一次 → 数据库唯一约束，最简单；
- **L2 跨视角级**：同一头猪在左/中/右三张图里 → 需要实体对齐或互斥 ROI 分区；
- **L3 跨栏舍级**：隔壁栏舍的猪被本栏舍点到（或反之）→ 需要边界裁剪 + 归属唯一性。

## 4. 需求里藏着的硬口径（可直接当验收用例）

1. **归属唯一**：一条盘点结果里的每个目标，只能归属一个栏舍；`Σ 栏舍数量 = 栋 = 场`，不允许重复计入。
2. **证据可反查**：任何一个数字都能反查到它引用的全部照片/视频帧、各自的 `roi` 与模型版本。
3. **未归属 = 0**：提交盘点时未归属照片必须为 0（或明确列入待裁决池，不进计数）。
4. **锁定不可逆**：已锁定照片删除必须失败；后台作废必须留审计（操作者、时间、原因、原值）。
5. **幂等**：同一次采集重传不产生第二条盘点；弱网重放后数量必须与首次一致。
6. **可复现**：同一批输入 → 同一结果（延续现有回放门槛的口径）。
7. **多日平均的统计前提**（需求 6 的关键风险）：**平均只有在"这几天猪只没变动"时才成立**。
   转群、出栏、死亡、并栏会让平均值失真。所以要么
   - 记录存栏变动事件，只对"变动区间内"的多次盘点做聚合；
   - 或改用**稳健口径**：中位数 / 去掉最高最低再平均 / 按照片质量加权平均；
   - 并且**保留每天的原始值**，综合值给的是"建议值 + 波动区间"，人工确认后才写入业务值（与现有 `review_required` 语义一致）。

## 6. 需要你确认的口径（不确认就只能猜）

1. **栏舍的定义**：是"一栋里的一个圈栏"（1 栋 20 个）吗？栏舍和"栏位"是什么关系？
2. **金蝶同步范围与方向**：只同步猪场/组织，还是也含栋/栏舍？ERP 里改了编码、本地也改过，谁赢？本地新增的栋/栏舍会不会被同步清掉？
3. **平均口径**：算术平均 / 中位数 / 去极值 / 按质量加权？要不要先剔除有存栏变动的日期？
4. **综合盘点的效力**：是直接作为账面存栏（并与金蝶对账），还是只作建议值、人工确认后生效？
5. **后台修改权限**：谁能解锁、谁能删已盘点照片、改完是否必须出差异报告？
6. **视频的口径**：视频是抽帧计数还是全程计数？视频和照片能否同属一次盘点？
7. **遮挡时允许输出什么**：允许"区间 + 置信度"，还是必须给一个确定数字？（这决定质量门能不能拦住不可靠的数）
8. **删除的性质**：未盘点照片的删除是物理删除还是逻辑作废？证据保留期多久（审计/合规要求）？
9. **是否接受扫码归属**（栏舍二维码/NFC，拍照前扫码）？我认为这是解决"照片不知道是哪个栏舍"最省钱、最可靠的办法。

## 7. 建议的落地顺序（每一步都能单独交付价值）

1. 三级主数据 + `penId` 绑定（含扫码归属）；
2. 采集包 → 栏舍照片/视频库（L1 哈希去重 + `可删/锁定/作废` 状态机）；
3. 单栏舍计数 + 质量门 + 越界过滤（`roi` 裁剪）；
4. 左/中/右多视角 + 互斥 ROI 分区 + 跨视角去重；
5. 多次盘点 session + 每日报告 + 综合盘点（稳健聚合）；
6. 金蝶同步与对账、后台解锁/作废与审计报表。
