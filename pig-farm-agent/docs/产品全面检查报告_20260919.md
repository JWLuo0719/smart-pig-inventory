## 0. 一句话结论

**设计是完整的，实现是分裂的。** 你有两个各自能跑、但互相不知道对方存在的产品：
`pig-farm-agent` 的 V2 设计（栏舍为原子单元的三平面架构）**一行都没实现**；
`smart-pig-inventory` 的全栈 App 已经是可运行的生产级代码，**但参赛材料里一个字都没提它**。
最要命的是：**两者的运行时其实是连在一起的**（App 配置的模型校验和，就是 Agent 仓库里那个 ONNX），
却没有任何一份文档承认这件事。

单看 `smart-pig-inventory`，工程质量明显高于一般学生项目（发布签名门禁、fail-closed 默认值、
路径穿越防护、组织隔离都做得对）。但**安全不变量在最关键的几条路径上是破的**：
推理任务在模型获批后会静默永久卡死（§5.2）、三图在已批准配置下会被相加（§5.3）、
ROI 在手机竖拍时会切错区域（§3 P1-1）。这三条都属于「平时不发作、一发作就是数据不可信或流程停摆」，
而且**前两条恰好都在 `MODEL_APPROVED=true` 的那一刻同时武装**——也就是这个产品的下一步。

另外两条**此刻就已经坏了**，不需要等任何开关：

- **出厂镜像里 PDF 导出直接 500**（§8.1）——镜像缺拉丁字体，而唯一的 PDF 测试被
  `@EnabledOnOs(OS.WINDOWS)` 挡在 Linux CI 之外，所以一直是绿的。
- **默认启动路径是 fail-open 的**（§8.2）——`SECURITY_ENABLED` 默认 `false` 时，
  认证、RBAC、组织隔离全部关闭，API 却通过网关发布在局域网上。

全篇共 **8 个 P0、20+ 个 P1**。它们分散在 4 个服务、3 种语言里，
但**没有一条是「设计错了」**——绝大多数是「默认值是危险的那一侧」和「关键的守卫没有断言返回值」。
这意味着它们是**可修的**，而且大多改动很小。

## 2. P0：必须在任何对外交付前处理

### P0-1　参赛材料漏掉了真正做出来的那个产品

- **证据**：`smart-pig-inventory` 在整个 `参赛材料\` 目录下命中 **0 次**
  （`Get-ChildItem 参赛材料 -Recurse | Select-String "smart-pig-inventory|智慧猪场场主"` → 0 命中）。
  商业计划书 `document.xml` 中 `smart-pig-inventory` 命中 0 次、`Flutter` 0 次、`Spring` 0 次、
  `采集包` 0 次、`幂等` 0 次；而 `移动端` 出现 21 次。
- **问题**：商业计划书写「当前已基本实现照片采集、可信清点、照片去重、盘点确认和日报流程」——
  这句话**只对 `smart-pig-inventory` 成立**。评委或导师若按参赛仓库（`pig-farm-agent`）核对，
  找不到照片去重、盘点确认、日报这些能力；反过来，真正实现了这些的仓库又完全没被提及。
- **建议**：在商业计划书「三、产品/服务」明确写清两个仓库的分工与关系，
  并把 App 的界面截图作为附录佐证（`检查报告_20260918.md` E3 已提出同一建议）。
  参赛仓库建议以 submodule 或直接合并的方式纳入 App 代码，或至少提供可访问的仓库地址。

### P0-2　`pig-farm-agent` 完全没有版本控制

- **证据**：`git rev-parse --show-toplevel` → `fatal: not a git repository`；根目录无 `.git`。
- **问题**：这是**参赛交付物本体**。没有历史、没有回滚、没有异地备份、没有 diff 审查。
  与 `smart-pig-inventory`（有 git、有 GitHub、有 CI）形成鲜明对比。
- **风险**：一次误删即不可恢复；`参赛材料` 里 40 MB 的评审产物也在同一目录下。
- **建议**：立即 `git init` + 首次提交，并写 `.gitignore` 排除 `.tools/`（4.97 GB）、
  `.venvs/`、`__pycache__`、`.pytest_cache`、`nul`。推到 GitHub 私有仓库。

### P0-3　`nul` 文件：一个无法正常打开、也无法正常删除的残留

- **证据**：根目录存在一个 34 字节、名为 `nul` 的文件；`Get-Content .\nul` 报
  `Cannot find path 'D:\pig-farm-agent\nul'`——因为 `nul` 是 Windows 保留设备名。
- **成因**：某次 shell 里写了 `> nul`（应为 `$null` 或 `NUL`）产生的重定向残留。
- **建议**：用 `\\?\` 前缀路径删除：`Remove-Item -LiteralPath '\\?\D:\pig-farm-agent\nul'`。
  这也说明为什么需要 P0-2 的版本控制——这类垃圾本该在 `git status` 里一眼看到。

### P0-4　推理任务会永久卡死，且管理端完全看不到

详见 §5.2。一句话：推理服务在「非 `succeeded` 状态 + 非空 count」时会透传 count，
Spring 拒绝并返回 422 → 推理侧归类为**永久失败**且**从不重试**、**也不发终态回调**
→ 任务永远停在 `processing`，而管理端失败列表只查 `status='failed'`，**运维无从发现**。
该组合完全符合契约 schema，属于合法输入触发。

**当前是否已发作**：否。现网配置是 `research-http-yolo`，而
`ResearchHttpYoloCountingProvider.count()`（`providers.py:154-163`）在降级时会**显式把 count 置空**，
所以今天走不到这条路径。**但它在 `MODEL_APPROVED=true` 的那一刻就会武装起来**
（`http-yolo` 路径不做置空，见 `providers.py:467-469`），
而「批准模型」正是这个产品的下一步计划。所以它是**潜伏的 P0，不是理论问题**。

### P0-5　`/files/` 可以下载整个数据库，且**配置了令牌也挡不住**

这是本次检查发现**最严重的单点安全缺陷**，已实测复现。

- **证据**：`server.py:247` 的路由正则是 `^/files/([\w./-]+)$`——接受任意文件名；
  `evidence.py:88-95` 的 `resolve()` **只校验「在 data_dir 之下」**，不限定子目录。
- **实测**（该 subagent 用一个指向 `%TEMP%` 的临时 data 目录做的黑盒探测，未污染仓库）：
  - `GET /files/agent.db` → **200**，响应体以 `SQLite format 3` 开头
  - `GET /files/events.jsonl` → **200**
  - **并且这两条在 `writes_protected=True` 且已正确配置令牌的情况下依然返回 200**
- **后果**：`requirements-v2.md` 把「局域网部署 + 只读看板开放」写成了正式部署方式
  （README 也给了 `PIG_AGENT_HOST=0.0.0.0` + `PIG_AGENT_API_TOKEN` 的配置示例）。
  在这种部署下，局域网内任何人——**无需任何凭据**——即可拖走整个事件库、
  `inbox/` 里的猪场原始照片、以及全部证据 JSON。令牌只保护写操作，
  恰恰是「配置了令牌所以以为安全了」的假安全感。
- **注意**：目录穿越本身**是防住的**（`..`、`..%2F`、`%2e%2e`、`....//`、`//etc` 实测全部 404）。
  问题不是穿越，而是**作用域没收窄**。
- **修复**：把 `/files/` 限定到 `data_dir/evidence/**`（resolve 后再对 `evidence_dir` 校验一次），
  按 `CONTENT_TYPES` 白名单后缀，其余一律要求令牌。

### P0-6　写操作可被跨站「简单请求」触发（CSRF）

- **证据**：`server.py:361`、`:374` 无论 `Content-Type` 是什么都按 JSON 解析请求体；
  而 `config.json:19` 出厂值是 `"api_token": null`，此时 `_require_token` 直接放行（`:227-228`）。
- **实测**：`POST /analyze` 与 `POST /events/{id}/ack` 带 `Content-Type: text/plain`
  （这是 CORS 的**简单请求**，浏览器**不发预检**）均返回 **200**。
- **后果**：操作员在浏览器里打开任意一个恶意页面，该页面就能对
  `127.0.0.1:8787` 创建事件、确认/关闭告警。看板把令牌存在 `localStorage`（`index.html:198-202`）
  且本机以 HTTP 提供服务，进一步放大了风险面。
- **修复**：强制要求 `application/json` / `multipart/form-data`（否则 415）；
  校验 `Origin` / `Sec-Fetch-Site`；绑定非 loopback 时**默认要求令牌**而不是默认为空。

### P0-7　出厂镜像里 PDF 导出直接 500

详见 §8.1。一句话：报表渲染器在构造时就要加载一个拉丁字体，
而 Docker 镜像里**根本没有这个字体**（只有 CJK 的 droid 字体），
于是 `GET /api/v1/inventory-reports/exports/pdf` 在容器里**必然 500**。
唯一的 PDF 测试带着 `@EnabledOnOs(OS.WINDOWS)`，在 Linux CI 上**根本不运行**，
而 CI 也从不构建这个镜像——所以这个 P0 一直是绿的。

**这条尤其要紧**：报表导出是「已确认盘点」的唯一出口，
也是 `PROJECT_STATUS.md` 里明确列出的已交付功能之一。

### P0-8　默认启动路径是 fail-open 的：认证、RBAC、组织隔离全部关闭

详见 §8.2。一句话：`SECURITY_ENABLED` 默认 `false`（连 `.env.example` 都是），
此时 `anyRequest().permitAll()`、`assertRole` 直接返回、
`activeOrganizationId()` 返回**组织表里的第一行**，而 API 通过网关发布在局域网上。
审计主体还会被写成字面量 `"local-dev"`，**审计链无法归属到人**。

## 3. P1：功能正确性问题（有实测证据）

### P1-1　EXIF 方向未纠正，ROI 裁剪会切错区域（跨三端）

这是本次检查发现的**最实质的功能缺陷**。

- **契约要求**：`contracts/openapi.yaml:7-8`「ROI 使用完成 EXIF 方向纠正后的图像坐标，并归一化到 0..1」；
  同文件 `:846`、`:850` 定义 `width/height` 为「完成 EXIF 方向纠正后的像素」；`:882` 再次强调。
- **App 侧做对了**：`apps/mobile/lib/core/storage/image_metadata_reader.dart:104-109`
  在 `orientation >= 5` 时交换宽高；`:114-116` 把 `orientation` 写进 `exif`。
  `media_materializer.dart` 原样流式拷贝原始字节，**不重新编码**——所以上传的 blob **保留了 orientation 5–8**。
- **服务端没做**：`services/inference-service/app/*.py` 对 `exif|transpose|orientation`
  **零命中**；`pig-farm-agent/research_runner/app.py:94-105` 的 `crop_by_roi()` 直接
  `Image.open(...).crop(box)`，没有 `ImageOps.exif_transpose()`；
  `:138-140` 的 `offset_x = roi.x * img.width` 同样基于未纠正的原始尺寸。
- **后果**：手机竖拍（orientation 6/8）等常见情况下，服务端在**未旋转的像素坐标系**里
  套用**已纠正坐标系**的 ROI 矩形 → 裁剪到错误区域。可能正好把**隔壁栏舍**裁进来，
  而「隔壁的猪不能算进来」正是需求裁决 C5 的核心。**且全程静默，不报错、不告警。**
- **建议**：在两个服务端的图像加载处统一加 `ImageOps.exif_transpose(img)`，
  并加一个 orientation=6 的夹具图片做端到端回归，断言裁剪区域正确。

### P1-4　`research_runner` 的 `/count` 无鉴权，且能代为访问 MinIO

- **证据**：`research_runner/app.py:120` `@app.post("/count")` 无任何鉴权依赖；
  `:201-204` `uvicorn.run(app, host="0.0.0.0", port=LISTEN_PORT)` 监听所有网卡。
  `:79-91` `fetch_object()` 用 Runner 自己的 MinIO 凭据去拉取**请求方指定的**
  `s3://bucket/key`。
- **后果**：同一局域网内任何人都可以（a）白嫖推理算力，（b）借 Runner 的凭据读取
  MinIO 中任意对象。这是一个 SSRF + 凭据滥用面。
- **建议**：加服务密钥校验（与产品侧 `INFERENCE_CALLBACK_TOKEN` 同款做法）；
  默认绑定 `127.0.0.1`，需要跨容器时再显式放开；对 `object_uri` 做 bucket 白名单。

### P1-5　单图会返回真实计数，安全边界只靠下游一层挡着

- **证据**：`research_runner/app.py:188-189`
  `"status": "review_required" if multi_view else "succeeded"`、
  `"count": None if multi_view else len(detections)`。
  **单图（`capture_kind == "single"`）会返回 `status="succeeded"` 和一个真实 `count`。**
- **问题**：`MODEL_APPROVED=false` 的未批准模型本不应产出可入账的计数。
  目前的实现是「Runner 照常给数，靠 Spring 的 `InferenceResultService` 强制降级为
  `review_required`」。安全属性是**单点**的——Spring 那一层一旦有回归（本项目历史上
  就出现过「晚到回调把已确认会话重新置为 review_required」这类边界 bug），
  未批准的计数就可能进业务值。
- **建议**：Runner 自身在 `MODEL_APPROVED=false` 时就不返回 `succeeded`/`count`，
  只返回检测框并置 `review_required` + warning。纵深防御，而不是把全部信任押在一层。

### P1-6　写操作的审计主体可以是匿名的

- **证据**：`server.py:375`
  `operator = str(body.get("operator") or body.get("operator_id") or "human")`。
- **问题**：`requirements-v2.md` 公理 A5「机器提议、人签字」与不变量 4
  「作废必须带操作者/时间/原因」要求签字可追溯到人。缺省填 `"human"` 使审计记录
  **无法归属到具体人**，等于把「签字」退化成「有人点过」。
- **建议**：`resolve`/`dismiss` 必须显式提供 `operator`，缺失即 400；`ack` 同理。

### 5.2 P0（潜伏，批准模型时即发作）：非 `succeeded` 状态下 count 被原样透传 → 任务永久卡死

  即：`review_required` / `failed` 状态下，上游给的 count **原样保留**。
  实测：`review_required` + `count=42` → 透传 42；`failed` + `count=7` → 透传 7。
- **后果链条**（这是真正严重的地方，已逐环独立复核）：
  1. 违反「`review_required` ⇒ `count` 必须为 null」不变量；

  4. `tasks.py:42-45` **只捕获 `TransientCallbackError`**，`PermanentCallbackError` 直接冒泡，
     **既没有重试，也没有终态回调**；
  5. 该任务永远停留在 `processing`，且因为
     `JdbcInferenceAdministrationRepository.java:40` 只查 `status='failed'`，

  `detections` 来给复核人看候选），应改为

### 6.1 P1：感知哈希对真实照片**永远不会生成**——文档里的近重复告警是死的

- **证据**：`lib/core/media/perceptual_hasher.dart:26` `_maximumPixels = 6 * 1000 * 1000`，
  在 `:40` `if (info == null || info.width * info.height > _maximumPixels) return null;`。
  而 `capture_screen.dart:169` 调 `pickImage(source: source, imageQuality: 92)`，
  **没有传 `maxWidth`/`maxHeight`** → 一台普通 1200 万像素手机的照片是 4000×3000 = **12,000,000 > 6,000,000** → 返回 null。
  已对照 `image` 包确认：`JpegDecoder.startDecode → JpegData().readInfo` 拿到的是**全画布尺寸**，
  `decodeFrame(0)` 也是**全分辨率解码**。
- **后果**：`queue_capture_draft.dart:140-151` 因此**在每一份真实清单里都省略 `perceptualHash`**，
  于是 `openapi.yaml` 里定义的 `/review/near-duplicates`（汉明距离 ≤ 8）**一次都不会触发**。
  也就是说，「错图/重复图告警」这个人无我有、写进需求追踪矩阵的能力，
  **在真机上从未生效过一次**。
- **测试为什么没发现**：`test/perceptual_hasher_test.dart:17,33` 只用了 64×64 和 9×8 的**极小图**，
  刚好都在上限之下；而 `docs/product/requirements-traceability.md:47` 却标着「已自动化验证」。
- **修复**（一行的事）：改用 `dart:ui` 的
  `instantiateImageCodec(bytes, targetWidth: 9, targetHeight: 8)` 让原生缩放解码，
  或把上限提到 ~50 MP 并在 `decodeFrame` 前先缩放。

### 6.2 P1：Drift 在两个 Isolate 中打开却没有 WAL / busy_timeout

- **证据**：`core/storage/app_database.dart:166-171` 用
  `NativeDatabase.createInBackground(databaseFile)`，**没有 `setup` / `beforeOpen`**；
  Drift 自己的文档（`drift-2.34.3/lib/native.dart:140-144`）说明默认的 rollback journal
  不允许并发读写，WAL 必须显式开启。
  而 `main.dart:22` 把这个连接持有一整个进程生命周期，
  `features/sync/outbox_background_sync.dart:35` 又从 **WorkManager 的 isolate** 打开**第二个** `AppDatabase` 指向同一文件。
- **后果**：任何一次并发写（操作员在后台 Worker 写租约/blob 状态时同时入队一次采集）
  都可能抛 `SQLITE_BUSY`，最终以 `capture_screen.dart:369-373` 的通用
  「未能写入上传队列」呈现——**用户看到的是无原因的失败**。
- **修复**：`setup: (db) { db.execute('pragma journal_mode = WAL'); db.execute('pragma busy_timeout = 5000'); }`
  再加一个 `MigrationStrategy.beforeOpen`。

### 6.3 P1：某栏舍无数据时，趋势卡显示的是**全场合计**

- **证据**：`features/inventory/inventory_reports_screen.dart:190`
  `final (label, points) = trend.seriesFor(penId) ?? ('', trend.total);`。
  `core/network/inventory_browse_api.dart:108-118` 对窗口内不存在的栏舍返回 null
  （他们自己的测试就是这么断言的：`test/trend_model_test.dart:54` `expect(trend.seriesFor('missing'), isNull)`）。

### 7.2 P1：产品的名字叫「DCR 可信重评分」，但这个重评分**从未被执行**

这是本次 Agent 审计里最伤的一条——因为它动的是产品的核心卖点。

- **证据链**：
  - `manifest.json:5-6` 声明 `score_mode = "quality_product"`、`score_power = 0.75`；
  - 而 `rescorer.json:105-106` 声明的是**互相矛盾**的 `score_mode = "multiplier"`
    （`final_score = score * clip(p_correct/max(score,1e-3), 0.05, 5.0)`）；
  - `model_runtime/scoring.py:77-100` 实现了 `quality_constrained_scores`（= score^0.75 · p_correct），
    **但产品里没有任何代码 import `model_runtime`**（只有测试 import）；
  - **也没有任何代码计算 `p_correct` 或那 21 维特征向量**（`rescorer.json:81-103`）。
  - 然而事件里照样写入 `score_mode`（`detector.py:271/307/403`）和
    `postprocess="onnx+linear-softnms"`（`:306`）。
- **后果**：`detector.py:335-338` 的注释自称「如实标注…不做静默冒充」，
  但**把 `score_mode="quality_product"` 写进每一个事件**、实际算的却是**原始 YOLO 置信度**——
  这正是它声称不会做的那种冒充。而「可信」（trustworthy）恰恰是答辩时的核心论点。
- **修复**：要么真的接上 `quality_constrained_scores` + `p_correct` 线性模型，
  要么把事件里的 `score_mode` 改成 `"raw"` 并加 `score_applied=false`，同时**统一两份互相矛盾的 JSON**。

### 8.4 已核实的数据完整性正面项

- **V10 真的用 SQL 强制了不变量**（值得明确写下来，因为文档语焉不详）：
  `current_confirmation_marker` 是 `GENERATED ALWAYS AS (CASE WHEN status='confirmed' THEN 1 ELSE NULL END) STORED`，
  配合 `UNIQUE (pen_id, business_date, current_confirmation_marker)`——
  因为 MySQL 唯一索引忽略含 NULL 的键，所以同栏同日可以并存任意多 `submitted`/`review_required`/`superseded`，
  但**第二个 `confirmed` 在数据库层不可能存在**。
- **回调重放不会覆盖已确认会话**：`markSessionForReview` 带
  `WHERE id = ? AND status NOT IN ('confirmed','superseded')` 守卫。
- **`confirm`/`correct` 的互斥是真的**，不只是 Java 层：两者都先
  `lockSession(...) FOR UPDATE` + `lockPen(...)` 再判重，V10 的唯一约束是 DB 兜底。
- **13 个迁移里所有外键都是默认 RESTRICT**，没有级联或孤儿路径；
  UUID 双向映射一致（`ByteBuffer.allocate(16)` 大端，与 MySQL `UUID_TO_BIN` 默认一致，
  且没有任何迁移用会静默换字节序的 `UUID_TO_BIN(...,1)`）。

### 8.5 已核实的 Spring 侧安全正面项

- **HMAC 比较处处恒定时间**：`InferenceCallbackAuthenticator.java:19-20` 与
  `MonitoringSecurityConfiguration.java:23-24` 都用 `MessageDigest.isEqual`，
  且**空白密钥即拒绝**（fail-closed）；`InferenceCallbackConfigurationValidator` 还拒绝
  「派发器开启但没有回调令牌」的启动。8 个参数化测试断言 `null`/`""`/`" "`/错误/大写/后缀全部 401，
  管理员 JWT 不可替代，且响应从不回显密钥。
- **监控端点隔离正确**：`@Order(1)` + `securityMatcher`，要求 `GET` + 精确密钥，
  认证失败与拒绝访问**都映射为 401**（不泄露密钥是否存在）。
- **零 SQL 注入**：所有用户值都是绑定参数；唯一拼接的 SQL 走封闭白名单
  （`table` 来自枚举 `switch`，`parentColumn` 来自三元表达式）。
- **跨组织读写处处被挡**：`activeOrganizationId()` 读的是**签名过的**
  `active_organization_id` claim（从不读请求字段），`assertRole` 每次调用都回查
  `organization_membership`，所以**在数据库里撤销角色会立即生效**，不必等 15 分钟令牌过期。
  跨组织一律返回 404 而非 403（正确选择，避免存在性探测）。
- **刷新令牌轮换是并发安全的**：`lockRefreshSession` 是 `SELECT ... FOR UPDATE`，
  旧会话在同一事务里被撤销并插入后继，复用已撤销令牌得 409 `REFRESH_TOKEN_REUSED`，
  存储的是 SHA-256 哈希而非原文。
- **XLSX 公式注入已防御且有测试**：报表字符串全部经 `cell.setCellValue(String)`
  产生**字符串**单元格，测试喂 `"=1+1"` 并断言 `CellType.STRING`。
- **CORS 是 fail-closed 的**：默认空列表、`setAllowCredentials(false)`、显式方法/头白名单。
- **密钥处理规范**：`${MYSQL_PASSWORD}` 等**无默认值**（缺即失败），
  `JWT_SIGNING_SECRET` 必须 Base64 且解码 ≥32 字节否则启动即抛，`.env` 已 gitignore 且未跟踪。

### 8.6 冻结的 Django 原型：确实没人用，但不是没有风险

**结论：主链路确实不用它**，四重独立验证——CI 不引用、8 个 compose 都不构建它、
28 个 `scripts/` 文件不引用、`business-api`/`inference-service`/`apps/`/`contracts/` 零代码引用；
25 个受跟踪文件里没有 `db.sqlite3`、没有 `.env`、没有提交凭据。七份文档声明其冻结。

但残留风险是真实的：

- **P2 许可证风险落在门禁之外**：`services/backend/requirements.txt:10` 钉了 `minio`——
  **AGPL-3.0** 的 Python SDK——并以**进程内链接**的方式用在 Django 应用里，
  而 `LICENSES.md:15` 明确禁止「AGPL/GPL 组件以…链接库或不可替换的产品内嵌方式进入主干」。
  唯一的自动许可证扫描（`ci.yml:43-45`）只覆盖 `services/inference-service`，
  其依赖里没有 `minio`，所以**这个问题永远不会出现在 SBOM 里**；
  而 `services/backend/Dockerfile:8` 一被构建就会分发它。
  **这是全仓库唯一一处 AGPL 库被「链接」而不是作为独立服务运行的地方。**
- **P2 半加固的默认值**：`config/settings.py:8` `DEBUG` 默认 `true`
  （同时开启静态媒体服务与详细 traceback）、`SECRET_KEY` 有 `unsafe-development-key` 兜底、
  `AUTH_PASSWORD_VALIDATORS = []`、`Dockerfile` 没有 `USER`（business-api 有 `uid 10001`）。
- **P3 命名混淆**：它是 `services/business-api` 的弃用兄弟，名字看不出区别，
  且 `Dockerfile` 仍是一条可用的构建配方。
- **建议**：改名为 `services/legacy-django-prototype` 或移到 `docs/legacy/`；
  删掉它的 `Dockerfile` 或加「DO NOT BUILD」头；`DEBUG`/`SECRET_KEY` 改为 fail-closed；
  把 `pip-licenses` 任务扩展到它的 requirements（或去掉 `minio`——反正没人跑）。

### 8.7 Spring 侧可维护性（P2/P3 择要）

- **上帝类**：`JdbcInventoryReviewRepository`（510 行、30+ public 方法、15 个嵌套 record）
  与 `InventoryReviewService`（439 行、17 个 public 方法）。
- **重复样板**：`bytes(UUID)`/`readUuid` 在 main 里**重复 12 次**、测试里 **9 次**，
  `ByteBuffer.allocate(16).putLong(...)` 出现 **34 次**——尽管已经有 `common` 包。
  而且副本之间**行为不一致**：`JdbcInferenceRepository.java:188-193` 遇到 SQL `NULL` 会 NPE
  并把全零 UUID 强制转成 `null`，而 `JdbcInferenceAdministrationRepository.java:164-167` 是 NULL 安全的。
- **四套并行的异常类型 + 四份手写的 RFC 7807 构造器**——这正是 1.3 的错配与 2.6 的
  `Map.of` 空值地雷（`Map.of` 拒绝 null，一旦 detail 为 null 就 NPE → 500）的温床。
- **分层违规**：`MasterDataAdministrationService`（在 `application/` 包）直接注入 `JdbcTemplate` 跑裸 SQL；
  `InventoryReviewController.java:113-118`（`ui` 类）把**基础设施类型**
  连全限定名一起当作公开响应契约返回。
- **误引入 MyBatis**：`pom.xml:57-61` 声明了 `mybatis-spring-boot-starter`，
  但**一个 mapper 都没有**——它唯一的作用是**传递提供 `spring-boot-starter-jdbc`**
  （项目自己没声明）。换成后者即可把 MyBatis 及其自动配置移出运行时与 SBOM。
- **`MinioStagedObjectStorage.java:76-77` 注释引用了一个不存在的 worker**：
  「An orphan cleanup worker will retry objects that could not be removed here.」——
  全 `src/` grep `orphan` 只有这句注释。于是每次 `deleteQuietly` 失败都会
  **永久且静默地泄漏一个对象**（失败提升时的暂存 blob、回滚提交时的证据 blob），
  无回收、无指标、无告警。

## 10. 值得肯定的地方（不是客套，是有证据的）

这次检查发现的**问题比预期多**，但同样有证据表明：这个项目的工程习惯明显好于一般学生项目。
下面每一条都是实测或逐行读出来的，不是鼓励。

- **`smart-pig-inventory` 的发布签名门禁做得很扎实**：
  `apps/mobile/android/app/build.gradle.kts:34-79` 的 `validateReleaseConfiguration`
  在缺密钥时**硬失败、无 debug 回退**，拒绝 Android Debug 证书，要求恰好一个
  `API_BASE_URL` dart-define，且必须是**无凭据、无 query、无 fragment、非 IP 字面量**的 HTTPS DNS 域名，
  并限制 LAN CA 只能用于 `pig-inventory.local`。这一段的质量高于多数商业项目。
- **App 的密钥处理干净**：令牌**只**存在 `flutter_secure_storage`；仓库内没有提交任何密钥/keystore；
  **明文流量只在 debug manifest 开启**；`lib/` 中**零 `print`/日志/`TODO`/`FIXME`**。
- **App 没有「假数据」这个失败模式**：`home_screen.dart:330,338` 在任务列表未知时渲染 `—` 而不是 `0`；
  `task_list_screen.dart:126` 未确认栏位显示 `—`；`session_review_screen.dart:291-292` 说
  「服务器未返回可用候选数量」而不是编一个；`test/home_task_state_test.dart:104` 明确断言
  加载失败后**不显示 `0 / 0`**。这正是文档反复警告的那个反模式，代码里真的没有。
- **Spring 的关键安全件是对的**：HMAC 处处恒定时间且**空白密钥即拒绝**；监控端点与用户认证完全隔离；
  **零 SQL 注入**；跨组织读写处处被挡且一律 404；刷新令牌轮换是 `FOR UPDATE` + 哈希存储；
  **XLSX 公式注入已防御并有测试**；CORS 默认空列表 fail-closed；`${MYSQL_PASSWORD}` 无默认值。
- **V10 用 SQL 真的强制了「同栏同日只有一个已确认版本」**（生成列 + 唯一索引 + NULL 语义），
  不是只靠 Java 判断。
- **推理服务的安全默认值是真的**：`MULTIVIEW_DEDUP_ENABLED` / `MULTIVIEW_AUTO_COUNT_ENABLED` /
  `VIDEO_AUTO_COUNT_ENABLED` / `VIDEO_COUNTING_ENABLED` / `MODEL_APPROVED` 全部默认关闭，
  全 `app/` grep 不到任何 mock/占位/随机数字，四条 fail-closed 路径都是真的。
  （**默认值正确 ≠ 不变量成立**——见 §5.2/§5.3，漏洞出在非默认路径上。）
- **证据文件路径穿越防护正确**：`evidence.py:88-92` 用
  `(root / rel).resolve()` 后 `relative_to(root.resolve())`，是标准写法；
