## 1. 产品定位

产品面向规模化猪场的场长、兽医和巡检人员，将栏舍摄像头、猪群计数和人工处置记录组织成可追溯的日常运营闭环：

```text
视频/图片 -> 可信计数 -> 异常发现 -> 证据解释 -> 处置建议 -> 人工确认 -> 日报与趋势
```

第一阶段产品是“只读分析 + 建议”的运营助手，不宣称疾病诊断，不直接控制风机、喂料器或其他设备。模型正式名称为 **DCR-SoftNMS-YOLOv13**（如论文定稿更名，以模型 manifest 和版本登记为准）；DRRA 是科研过程中的历史架构名，不作为产品模型名。

### 与 smart-pig-inventory App 的兼容策略

`smart-pig-inventory` 继续作为现有现场采集入口。`D:\pig-farm-agent` 提供统一 Agent API，App 通过 HTTPS/局域网 HTTP 上传图片或视频帧、查询分析结果并提交人工确认；Web 看板复用同一 API 做管理和日报。模型推理、风险规则和事件状态只在 Agent 后端实现，避免 App 与 Web 各自维护一套业务逻辑。V1 先兼容 App 的上传和结果展示流程，再逐步增加批量上传、离线队列和推送通知。

## 2. 客户价值与商业闭环

| 客户问题 | 产品能力 | 可量化价值 |
|---|---|---|
| 人工点猪慢且结果不稳定 | 密集场景计数、置信度和复核证据 | 减少重复巡栏，建立统一口径 |
| 异常发现滞后 | 按栏舍的密度、卧躺、活动变化告警 | 缩短发现到复核的时间 |
| 告警过多、无法判断 | 风险分级、证据卡片、建议动作 | 让告警可处理、可追踪 |
| 处置经验难沉淀 | 确认/驳回/备注/关闭记录 | 形成场内数据资产和复盘依据 |

收费建议按“栏舍数 + 分析频次 + 服务等级”组合，而不是按模型调用次数计费。首批客户采用试点合同，交付一个猪舍或一个生产单元，验收后再扩展到全场。

## 3. 版本路线图

### V1：可用的巡检与告警闭环

目标是让一个真实用户每天使用并完成处置闭环。

- 输入：单张图片、短视频抽帧或定时摄像头快照；支持手工上传和目录轮询。
- 感知：猪只检测/计数、密度分区和输入质量；卧躺比例、活动变化列为试点验证项，未完成标注与验收前不作为已交付能力。
- Agent：规则和轻量统计模型完成风险分级；每条告警带时间、栏舍、指标、证据图和建议动作。
- 交互：Web 看板、告警列表、详情复核、确认/驳回/备注、日报导出。
- 部署：单场局域网或边缘主机，断网可继续分析，联网后同步信息。
- 验收指标：计数误差 MAE ≤ 5 头/图（按试点场景设基线）；高风险告警证据完整率 ≥ 95%；事件写入成功率 ≥ 99%；单张图端到端处理 ≤ 3 秒（边缘 GPU），CPU 降级可用。

V1 明确不包含个体身份识别、疾病诊断、多传感器融合、自动设备控制和跨场预测。

> 实现状态见 `docs/v1-technical-development.md` §11.1 与 `docs/v1-gap-list.md`：
> 手工上传、目录轮询、Web 看板、日报、写保护与回放门槛已落地；
> 待办集中在真实制品基线、7 天稳定性长跑和 App 真机联调。

### V2：多栏舍趋势与协同处置

- 接入时序数据库、企业微信/钉钉通知和多用户权限。
- 支持栏舍基线、日/周趋势、拥挤热区和活动/卧躺异常的持续检测。
- 引入人工反馈学习：记录告警是否有效、动作是否完成，用于阈值校准和模型再训练。
- 提供租户、猪场、栋舍、栏位四级数据隔离和审计。

### V3：生产决策与受控联动

- 融合温湿度、气体、采食、饮水和设备状态数据。
- 对转群、通风、饲喂排程提供情景分析和成本影响估算。
- 设备联动采用白名单、双人确认、限幅和回滚策略，默认保持人工审批。
- 在多场数据达到覆盖要求后再评估跨场泛化和预测性维护。

## 4. V1 产品模块

1. **数据接入**：兼容 App 上传、目录轮询和摄像头快照；记录来源、设备和时间。
2. **可信清点**：调用 DCR-SoftNMS-YOLOv13，保留候选、最终框、分数和模型版本。
3. **状态计算**：按栏舍计算数量、密度、输入质量和跨快照计数变化；行为指标只有在现场数据验证后才启用。
4. **风险引擎**：可配置阈值、连续帧确认、冷却时间和升级策略。
5. **证据与处置**：原图/标注图/指标快照、建议动作、人工确认和备注。
6. **报告**：日报、未关闭事件、栏舍排行和 CSV/JSON 导出。

## 5. 里程碑与交付物

| 周期 | 里程碑 | 交付物 |
|---|---|---|
| 第 1–2 周 | 契约冻结 | 事件 schema、模型 manifest、试点场景和验收口径 |
| 第 3–5 周 | 感知链路 | 模型 runtime、图片/视频输入、质量检查和证据图 |
| 第 6–8 周 | Agent 闭环 | 风险规则、告警状态机、建议动作、人工确认 |
| 第 9–10 周 | 看板与报告 | Web 看板、筛选、日报导出、权限最小实现 |
| 第 11–12 周 | 试点验收 | 7 天稳定性报告、误报复盘、部署手册和回滚包 |

## 6. 关键经营指标

- **使用**：试点场每日活跃用户 ≥ 2；每周有效巡检天数 ≥ 5。
- **效率**：从告警生成到首次确认的中位时间 ≤ 30 分钟；日报生成 ≤ 1 分钟。
- **质量**：高风险事件人工确认有效率 ≥ 70%；证据缺失率 ≤ 5%。
- **留存**：试点 4 周后仍有 ≥ 60% 的日常巡检使用率。
- **商业**：首批 3 个试点中至少 2 个愿意扩展到更多栏舍，并形成可引用案例。

## 7. 风险与边界

- **域偏移**：不同光照、角度、品种会影响计数；上线前必须用试点数据校准，低质量输入进入“需复核”而不是强行给结论。
- **模型漂移**：每次模型更新必须带版本、验证集指标和回滚包；生产环境禁止覆盖式更新。
- **告警疲劳**：采用连续帧确认、冷却和每日上限，保留全部原始事件供审计。
- **责任边界**：产品输出运营风险和复核建议，不输出疾病诊断或自动处置指令。
- **数据安全**：默认本地部署，图片按保留策略清理；租户和角色权限在 V2 完整化。

## 8. 成功标准

V1 不是“模型演示”，而是一个可在单栋猪舍连续运行 7 天的闭环系统：用户能看到可信结果，能理解告警依据，能完成确认和备注，第二天能用日报复盘；出现模型或服务异常时，系统给出明确的“数据不足/服务不可用”状态并允许回滚。
