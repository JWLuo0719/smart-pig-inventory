# 产品需求基线 V2（重构版）

> 本文取代此前分散的口述需求与 `docs/product-brief.md` 中的定位表述。
> 配套设计见 `docs/product-design-v2.md`；原始需求解读见 `docs/inventory-requirements-digest.md`。
>
> **变更动因**：① 原始 8 条需求混了三个不同性质的问题（主数据 / 感知计量 / 控制执行）；
> ② 客户新增"每圈独立控制"，属范围变更；③ 四条需求之间本身存在冲突，未裁决前无法设计。

---

## 1. 为什么必须重构（三个诊断）

**诊断一：原需求把三个不同"平面"的需求写在了一张清单里。**

| 平面 | 需求例子 | 一致性要求 | 延迟要求 | 失效后果 |
|---|---|---|---|---|
| 主数据平面 | 猪场/栋/栏舍、金蝶同步 | **强一致**（主键必须唯一稳定） | 天级 | 数据错位、喂错圈 |
| 证据平面 | 照片/视频采集、去重、照片库、盘点 | 最终一致（可延迟上传） | 分钟~小时级 | 数字不可信 |
| 控制平面 | 每圈独立控制 | **绝不接受脏数据** | 秒级 | **死猪** |

三个平面的要求互相冲突（强一致 ↔ 弱网容忍 ↔ 实时安全）。**把它们设计成同一套接口，是这个项目最大的技术风险。**

**诊断二：原始 4 个问题全部是感知问题，但客户的目标是控制。** 需要承认并显式化：
盘点不是终点，是控制系统的**参数标定环节**。

**诊断三：四条需求自相矛盾，必须由业务方裁决**（见 §4），否则实现时只能靠猜。

## 2. 六条设计公理（重构后的定位）

这六条是后续所有设计决策的裁判依据，任何设计冲突都用它们裁决：

| # | 公理 | 含义 | 直接后果 |
|---|---|---|---|
| **A1** | **一切挂 penId** | 栏舍（圈）是唯一的原子单元；照片、证据、头数、传感器、控制点、告警、成本全部以 `penId` 为主键挂载 | 场/栋只是汇总视图；不存在"属于栋但不属于任何圈"的数据 |
| **A2** | **慢变量与快变量分离** | 头数/日龄/体重曲线是慢变量（批次级变更）；采食/饮水/温湿度/氨气是快变量（分钟级） | **视觉盘点是慢变量的校准手段，不进安全回路**；日常控制靠连续量 |
| **A3** | **三平面隔离** | 主数据、证据、控制三个平面独立演进、独立接口、独立失效域 | 控制平面不得依赖证据平面上传成功；断网时控制仍闭环 |
| **A4** | **只增不改** | 证据与业务值 append-only；更正 = 新增版本 + 审计，不覆盖、不物理删除已引用的证据 | "删除"变成"作废"，责任可追溯 |
| **A5** | **机器提议、人签字** | 业务值由人确认后才生效；只有白名单动作允许自动执行。**签字分级**：低风险/低价值可批量确认，异常与高风险逐条确认 | `review_required` 是**责任边界**，不是功能缺陷；但"每圈每天逐条签字"在现场不可执行，必须分级 |
| **A6** | **断网可用** | 舍内无网是常态。采集、浏览、确认、控制闭环在本地全部可用；**离线签字必须可追溯到人且防抵赖** | 云侧只做聚合与治理，不做实时依赖 |

## 3. 需求分层（Must / Should / Won't）

### 3.1 Must —— 不满足则产品不成立

| ID | 需求 | 验收口径 |
|---|---|---|
| M1 | 猪场 / 栋 / 栏舍三级主数据，编码唯一稳定；猪场与组织来自金蝶 ERP，栋与栏舍本地维护 | 编码冲突为 0；同步有对账报告；本地扩展字段不被同步覆盖 |
| M2 | 采集证据必须归属到栏舍；支持"扫码后拍"（强绑定）与"拍后归位"（弱绑定，留痕） | **未归属照片不得参与任何计数**；弱绑定记录操作者与时间 |
| M3 | 离线采集与幂等上传：断网可拍、可存、可浏览；恢复后按栏舍断点续传；重传不产生第二条盘点 | 断网 24h 采集零丢失；重放 100% 幂等 |
| M4 | 栏舍证据账本（照片/视频库）：按 `栏舍 × 业务日期` 可翻阅、可检索 | 任一数字都能反查到它引用的全部证据 |
| M5 | 三层去重：① 文件级（`sha256` 全局唯一）② 视角级（同一 `penId × businessDate` 内互斥分区，**跨采集包也不得重复计入**）③ 跨栏舍（越界目标进待裁决池） | 同哈希重复引用 = 0；跨视角/跨包重复计入 = 0；越界目标只能归属一个栏舍 |
| M6 | 栏舍级计数：质量门 → 按标定边界裁剪 → 检测 → 去重 → 越界过滤 → 输出**数量 + 波动区间 + 证据 + 标定版本**；质量门**必须在真机模型路径下可触发** | 计数误差 MAE ≤ 5 头/圈（须写明统计口径）；质量不达标输出待复核而非硬值 |
| M7 | 复核、锁定、作废与审计：已盘点证据锁定；更正走版本化留痕 | 锁定后可篡改 = 0；每次变更含操作者/时间/原因 |
| M8 | 每日盘点报告 + 多日稳健聚合（综合盘点） | 聚合只覆盖"无存栏变动"区间；保留每日原值；综合值为建议值待确认 |
| M9 | 边缘部署与模型升级门槛：场内主机可自治；模型升级必须过回放门槛 | 场内断网可推理；升级差异即失败（沿用现有 `replay` 口径） |
| M10 | **身份与权限**：账号来源（对接既有账号体系）、角色（采集 / 复核 / 管理 / 控制）、租户与数据隔离、离线确认的签字凭据（防抵赖） | 越权操作 = 0；离线确认可追溯到人且不可否认；跨租户数据不可见 |
| M11 | **时间口径**：`businessDate` 由服务端按场区时区判定；服务端另记 `receivedAt`；手机时钟偏移超阈值时拒绝或改按服务端时间落账 | 因时钟问题导致的跨日错分 = 0；审计时间可对账 |
| M12 | **容量与保留**：原图/视频保留期、月度存储与带宽预算；原图与预览图两级上传 | 存储不超预算；弱网下优先传预览图以保证"当天能出数" |
| M13 | **几何标定**：栏舍边界（按机位）与机位姿态的标定责任人、版本与有效期；机位漂移可发现、失标定即失效 | 越界判定在同一标定版本内可复现；机位被挪动后旧标定不得继续生效 |

### 3.2 Should —— 控制路线的支撑能力（R4–R6）

| ID | 需求 | 说明 |
|---|---|---|
| S1 | 控制点建模：每圈执行器（料线/料阀/风机/湿帘/加热/照明/水阀/报警）及其粒度、协议、可达性 | 这是控制可行性的**前置事实**，不是软件问题 |
| S2 | 影子模式：系统只算不下发，输出建议设定值，人工执行并记录对比 | 进入半自动的唯一入场券 |
| S3 | 慢变量校准闭环：已复核盘点数 → 按圈饲喂/通风设定值 → 采食/环境反馈修正 | 头数只调设定值，**不调安全阈值** |
| S4 | 视觉异常检测：采食/饮水异常、堆叠不动、空栏、密度异常 | 视觉在控制场景的真正价值所在 |
| S5 | 环境传感与安全联锁：温湿度/氨气/CO₂ + 硬联锁（超温开窗、断电开窗、断网保通风） | 安全回路**独立于 AI** |
| S6 | 指令审计与回执：下发、回执、超时、失败、人工覆盖全部留痕 | 指令回执成功率 ≥ 99.9% |

### 3.3 Won't —— 本期明确不做（写下来比不写更有价值）

| 不做 | 原因 |
|---|---|
| 个体身份识别（哪头猪是哪头） | 现场收益不明确，成本高，且非本需求所需 |
| 疾病诊断 | 需要兽医资质与临床数据，产品定位不宣称 |
| 跨场预测 | 样本量与合规均不具备 |
| ERP 财务记账 | 本系统只出"按圈消耗清单"，账由金蝶记，避免两套账 |
| 硬件生产/改造总包 | 本系统只定义适配与验收规范，硬件由集成商负责 |
| GPS 定位、自由文本 EXIF | 隐私与合规（对齐 App 契约白名单） |
| 高风险动作全自动 | 通风最小量、下料量长期保留人工确认；自动化只覆盖白名单 |
| 实时精确计数 | 头数是慢变量，实时精度是伪需求（A2） |

## 4. 需求冲突裁决（重构的核心产出）

原需求里这 8 处互相打架，逐条给结论：

| # | 冲突 | 裁决 | 依据 |
|---|---|---|---|
| C1 | 需求 4 "错误照片可删" ↔ 需求 5 "已盘点不可删" | **未引用的可物理删；已被盘点引用的只可作废（逻辑删除 + 留痕 + 原图保留期）** | A4 |
| C2 | 需求 3 "拍照即出数" ↔ 舍内弱网 | **双通道**：端侧轻量推理给"预估值"（不出业务值、明确标注）；云端/边缘全量推理给正式值 | A6 + A5 |
| C3 | 需求 6 "多日取平均" ↔ 期间猪只可能变动 | **只在无存栏变动区间聚合**；改用中位数/去极值/按质量加权；保留每日原值；综合值为建议值 | A2 + A5 |
| C4 | 需求 8 "多视角去重" ↔ 实际很难做到完美的跨视角实体匹配 | **工程解法优先**：拍摄规范 + 互斥 ROI 分区（重叠带只归一段）+ 机位标定；跨视角匹配作为增强项 | 可验证性优先于算法优雅 |
| C5 | 需求 7 "隔壁的猪不能算进来" ↔ 实地拍摄必然拍到邻栏 | **边界标定 + ROI 裁剪 + 越界过滤 + 待裁决池**；宁可少算进人工队列，不允许静默地多算 | A1 + A4 |
| C6 | 控制需求 ↔ 现有 V1 "不控制设备" | **显式范围变更**：影子期 → 白名单半自动 → 闭环，逐级放行 | A5 |
| C7 | 金蝶同步 ↔ 本地维护栋/栏舍 | **字段级真源**：ERP 管组织/猪场（唯一真源）；栋/栏舍本地为真源；同步冲突按字段裁决并出对账报告 | M1 |
| C8 | 视觉精度 ↔ 控制安全 | **视觉不进安全回路**；安全阈值由环境传感器与硬联锁驱动 | A2 + A3 |

## 6. 开放决策（需客户/现场回答，按阻塞程度排序）

**阻断级——不确认无法开工：**

1. **实现归属裁决（需与 App/Spring 团队共同确认）**：证据账本、主数据、复核谱系到底由谁实现？
   若沿用 `docs/app-integration-contract.md` 的推荐路径 B（本 Agent 只做推理 Provider），
   本仓库在 R0/R1 的交付物是什么？**此条不裁，主数据与账本层的改造方向必然返工。**
2. **执行器粒度与安全承载方**：每圈是否有独立风机/风阀、独立下料执行器？有无本地 PLC 与协议？
   硬联锁与 fail-safe 由谁承载（PLC / 经认证控制器，还是通用主机）？
   （拿 `docs/pen-control-requirements.md` §2 核查表去现场逐项填）
3. **几何标定责任**：栏舍边界与机位标定谁提供、谁标、多久重标？机位被猪拱偏或被挪动如何发现与追责？
   （M5 / C4 / C5 三条 Must 的**共同前提**，此前完全缺失）
4. **安全兜底条件**：断电/断网时期望行为？有无 UPS / 应急开窗？每圈是否有独立环境传感器？
5. **责任边界**：客户是否接受影子期与误控责任条款？

**重要级——不确认会返工：**

6. **视频口径与容量预算**：视频是否参与计数？端侧抽帧还是边缘抽帧、时长上限多少？
   抽帧结果如何与外部契约的 `assets[1..3]` 约束共存？
   每月可承受的存储与上行带宽是多少？是否接受"只传预览图、原图延后补传"？
7. **身份与账号**：账号来源（是否复用 App/Spring 的账号体系）？角色划分？离线签字凭据形式？
   逐条签字的工作量客户能否接受，还是要批量确认？
8. **待裁决池 SLA**：谁处理待归属/越界目标、多久内处理、**超时是否阻塞当日报告**？
9. **报警值班与升级**：报警后谁响应、多久响应、未确认如何升级？（决定控制侧的兜底设计）
10. **栏舍定义**：确认 = 一栋内的圈栏（1 栋 20 圈）；栏舍与"栏位"的关系。
11. **金蝶同步范围**：只同步猪场/组织，还是也含栋/栏舍？冲突谁赢？
12. **综合盘点的效力**：直接作账面存栏（与金蝶对账），还是仅建议值？
13. **聚合口径**：中位数 / 去极值平均 / 按质量加权？（推荐：去极值 + 质量加权，且保留每日原值）
14. **后合作废权限**：谁能解锁与作废？是否强制出差异报告？

**可边做边定：**

15. 证据保留期（审计/合规要求）——需与 M12 的存储预算一起确定。
16. 扫码归属的接受度与频次：每张照片扫一次，还是进入栏舍采集会话后连拍只需扫一次（推荐后者）。
